# Static analysis: EWSUsgs, 2026-11-01

## Scope

- Repository: `AI-MINTT/EWSUsgs` (public). This review covers everything in the repo.
- Baseline: `main` at `29e4668` ("feat: initial commit for EWS USGS seismic risk service").
- Fixes: branch `fix/static-analysis-2026-11`. Nothing has been pushed.
- Files reviewed: `main.py` (175 lines at baseline), `requirements.txt`, `.gitignore`.
- Git history: all refs searched with `git log -p --all`. There is one commit.

The service is a FastAPI app. `GET /api/v1/risk/point` queries the USGS FDSN event
service for M>=2.5 earthquakes within 300 km over the last 30 days and turns them into a
risk score. `GET /health` is a liveness check. The AI-Mint_Backend gateway calls it
(`HttpEarthquakeRiskClient`, `Ews:EarthquakeUrl = http://localhost:8006`,
`Ews:TimeoutSeconds = 15`). The gateway passes this service's error body through
unchanged (`"EWSUsgs returned {code}: {body}"`).

### Checked, no finding

- **Secrets and internal hosts:** none in the code or the history (see above).
- **Timeouts:** the baseline already set an 8 s client timeout. Per-attempt timeouts are now capped by the 12 s budget.
- **Timezones:** all datetimes are timezone-aware UTC. USGS `starttime` is a UTC date. The event `time` (epoch ms UTC) is passed through untouched and not used in scoring.
- **Duplicate alerts and alert thresholds:** the service sends no alerts and keeps no alert state. It only aggregates per request, and USGS returns unique event ids. Not applicable.
- **Loops:** none. **File writes:** none. **Broad excepts:** none; only specific httpx, `ValueError`, `KeyError`, `IndexError` and `TypeError` exceptions are caught.
- **Input validation:** `Query(ge=..., le=...)` already rejects out-of-range, NaN and infinite lat/lon with a 422. The explicit `isnan`/`isinf` check in `risk_point` is redundant defence in depth and was kept.
- **bandit and semgrep:** 0 findings before and after the fixes (bandit's `S` rules are also covered by ruff).

## Verification

Offline sanity test, run with no network access. The script sits outside the repo and is
not committed. It used a throwaway virtualenv on Python 3.13.7 with fastapi 0.162.0,
uvicorn 0.54.0, httpx 0.28.1, starlette 1.10.0 and pydantic 2.14.2, and replaced the
module's client with an `httpx.MockTransport` that serves canned USGS replies. All
**27 of 27 checks passed**:

- A sample FeatureCollection with 2 valid features and 4 bad ones (non-numeric
  coordinates, NaN coordinates, null magnitude, null geometry) gives 2 events, the
  expected composite (0.865) and confidence (0.44), and a timezone-aware UTC timestamp.
- The expected query parameters and `User-Agent` are sent.
- An empty collection gives composite 0.0 and confidence 0.4.
- A JSON list, a missing `features` member, a non-list `features` member and an HTML body
  each give 502.
- 503 followed by 200 gives 200 after exactly 2 upstream calls. Two 503s give 502 after
  2 calls, and the detail does not contain the URL. A 429 or 400 gives 502 after 1 call.
  A `ConnectError` followed by 200 gives 200. Two timeouts give 502 `ReadTimeout`.
- 5 identical requests make 1 upstream call. A new point, or an expired cache entry,
  triggers a refetch. The cache stays within its bound.
- 200 events produce the truncation note.
- `lat=95` and `lat=nan` give 422. `/health` gives 200.

Before the fixes, the same harness reproduced the baseline problems: a JSON list gave 500,
a missing `features` member gave **200 with composite 0.0**, string coordinates gave 500,
the 502 detail contained the full USGS URL, and 5 identical requests made 5 upstream calls.

As a smoke test, `python -m uvicorn main:app --host 127.0.0.1 --port 18606` was started
under `timeout 10`. `/health` returned 200 and `lat=999` returned 422, and the process
had exited by the end of the check. No alerts or messages were sent anywhere.

## Recommendations (not done here)

1. Lock the transitive dependencies with hashes, for example
   `pip-compile --generate-hashes`, and install with `pip install --require-hashes`.
   Add a CI job that runs `pip-audit`.
2. Make the decision on EWS-09 (confidence monotonicity) and EWS-10 (hypocentral
   distance), then version the scoring change.
3. Commit an offline test, similar to the harness above, together with a
   `requirements-dev.txt`.
4. If the service is ever exposed beyond localhost, add authentication or rate limiting
   in front of it.
